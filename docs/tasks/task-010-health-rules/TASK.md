# TASK-010 — Настраиваемые правила светофора

| Поле | Значение |
|---|---|
| **Статус** | 📋 Запланировано |
| **Приоритет** | `P0` |
| **Релиз** | 0.2.0 — «Данные, которым можно доверять» |
| **Эпик** | Аналитика |
| **Оценка** | 3–5 дней |
| **Зависимости** | [task-003-persistence](../task-003-persistence/TASK.md) для сохранения правил |

## User Story

> Я как руководитель портфеля, хочу настраивать пороги «жёлтого» и «красного»,
> чтобы светофор соответствовал регламентам компании, а не был жёстко зашит в код.

## Зачем это нужно

Сейчас правила зашиты в `getProjectHealth`:

- просрочка закрытия > 0 → красный;
- любой перерасход → красный;
- меньше 3 месяцев до закрытия, нет выполненных целей и есть перерасход
  или просроченная цель → жёлтый.

Для одних компаний перерасход на 5% — норма, для других — критично. Для одних
просрочка на месяц — проблема, для других — допустимо. Без настройки дашборд
показывает неверную картину и подрывает доверие к светофору.

## Область работ

### Входит

- Экран «Правила светофора» в настройках.
- Параметры:
  - `overdueMonthsRed` — через сколько месяцев просрочки проект становится красным;
  - `budgetOverrunPercentRed` — допустимый перерасход в процентах;
  - `monthsToCloseYellow` — за сколько месяцев до закрытия включать жёлтый;
  - `minGoalProgressYellow` — минимальный прогресс целей для жёлтого;
  - `goalOverdueCountYellow` — сколько просроченных целей включают жёлтый;
  - `closedWithOverrunRed` — считать ли перерасход у закрытого проекта красным.
- Пресеты:
  - «Строгий» — просрочка 0 мес, перерасход 0%, жёлтый за 6 месяцев;
  - «Стандартный» — текущее поведение;
  - «Мягкий» — просрочка 1 мес, перерасход 10%, жёлтый за 3 месяца.
- Предпросмотр: сколько проектов станут красными/жёлтыми/зелёными при новых правилах.
- Сохранение правил (через `localStorage` или task-003).
- Сброс к стандартным правилам.
- Объяснение статуса: какие правила сработали.
- Валидация: числа в допустимых диапазонах, нет отрицательных значений.
- Миграция старых сохранённых правил.

### Не входит

- Индивидуальные правила для каждого проекта (можно добавить позже).
- Правила по направлениям и руководителям.
- Машинное обучение и автоматический подбор порогов.
- Учёт сезонности и праздников.
- Сложные булевы выражения.

## Модель правил

```json
{
  "overdueMonthsRed": 1,
  "budgetOverrunPercentRed": 0,
  "monthsToCloseYellow": 3,
  "minGoalProgressYellow": 0,
  "goalOverdueCountYellow": 0,
  "closedWithOverrunRed": true
}
```

## Сценарии

1. **Изменение порога.** Руководитель ставит перерасход 10%. Проект с перерасходом 5%
   перестаёт быть красным и становится зелёным.
2. **Предпросмотр.** До сохранения видно: «Станет красными: 2 (было 3), жёлтыми: 1».
3. **Сброс.** Пользователь нажимает «Сбросить», возвращаются стандартные значения.
4. **Объяснение.** Под карточкой проекта видно: «Красный: просрочка 2 мес (порог 1 мес)».
5. **Валидация.** Пользователь вводит −5 месяцев — поле подсвечивается, сохранение блокируется.
6. **Перезагрузка.** Правила сохраняются и применяются при старте.

## Критерии приёмки

- [ ] Все параметры из модели доступны в UI.
- [ ] Есть три пресета и кнопка сброса.
- [ ] Предпросмотр показывает изменение количества статусов.
- [ ] Правила сохраняются и восстанавливаются.
- [ ] `getProjectHealth` использует правила, а не константы.
- [ ] Под карточкой видно, какое правило сработало.
- [ ] Некорректные значения не сохраняются.
- [ ] Старые сохранения мигрируют без потери данных.
- [ ] Изменение правил не ломает фильтры и таблицу целей.
- [ ] Есть тесты на граничные значения (0, ровно порог, чуть больше).

## Технические заметки

- Создать `healthRules.js`:
  ```js
  const DEFAULT_HEALTH_RULES = { ... };
  const PRESETS = { strict: {...}, standard: {...}, soft: {...} };
  function normalizeRules(input) { ... }
  function validateRules(rules) { ... }
  ```
- Изменить сигнатуру:
  ```js
  getProjectHealth(project, rules = DEFAULT_HEALTH_RULES, today = TODAY)
  ```
- Вернуть не только `status`/`label`, но и `reasons`:
  ```js
  { status: 'red', label: '🔴 Проблема', reasons: ['просрочка 2 мес (порог 1 мес)'] }
  ```
- Сохранять правила отдельно от состояния или внутри `dashboard_state_v1`
  (`healthRules`), согласовать с task-003.
- При миграции: если правил нет — использовать `DEFAULT_HEALTH_RULES`.
- Порядок приоритетов: сначала red, потом closed, потом yellow, иначе green.
  Проверить, что закрытый проект с перерасходом ведёт себя предсказуемо.
- Не считать проценты через строки; округлять аккуратно.

## Риски и открытые вопросы

- Слишком гибкие правила могут сделать светофор непредсказуемым.
- Нужно ли разрешать разные правила для разных направлений?
- Кто имеет право менять правила? Зависит от task-001.
- Как объяснять пользователю, почему проект зелёный, если правило сложное?
- Что делать, если правила противоречат друг другу (например, жёлтый порог больше красного)?
- Нужно ли версионировать правила и хранить историю изменений?
