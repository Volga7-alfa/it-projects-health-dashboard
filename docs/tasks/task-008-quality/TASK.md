## User Story

> Я как разработчик, хочу покрыть правила светофора тестами, чтобы изменения
> не ломали логику статусов незаметно.
>
> Я как разработчик, хочу разбить `app.js` на небольшие модули, чтобы код было проще
> читать, тестировать и расширять.
>
> Я как разработчик, хочу автоматически проверять тесты и синтаксис на каждый коммит,
> чтобы не отдавать в прод сломанную версию.
>
> Я как пользователь, хочу видеть человеческое объяснение ошибки DeepSeek или Excel,
> чтобы понимать, что делать: проверить ключ, файл или соединение.

## Зачем это нужно

Сейчас вся логика находится в одном `app.js` на 567 строк. Расчёт здоровья, фильтры,
рендер, Excel и DeepSeek связаны. Любое изменение правил светофора проверяется вручную,
а ошибки API показываются техническим текстом. Это замедляет развитие и повышает риск
регрессий.

## Область работ

### Входит

- Выделение чистых функций в отдельные файлы:
  - `health.js` — расчёт просрочки, здоровья, причин;
  - `filters.js` — фильтрация проектов и целей;
  - `errors.js` — преобразование ошибок в понятные сообщения;
  - `storage.js` — из task-003, если ещё не выделен.
- Тесты на `node:test` + `node:assert` (без внешних зависимостей).
- `package.json` со скриптами `test`, `check`.
- CI-workflow GitHub Actions: проверка синтаксиса и тесты.
- Понятные сообщения об ошибках:
  - нет ключа;
  - неверный ключ (401);
  - нет средств (402);
  - лимит запросов (429);
  - сервер недоступен (5xx);
  - нет сети;
  - Excel не читается;
  - пустой файл;
  - DeepSeek вернул не-JSON.
- Небольшой чек-лист ручной проверки в `README` или `TASK.md`.

### Не входит

- Перевод проекта на TypeScript.
- Полный редизайн архитектуры и переход на фреймворк.
- E2E-тесты в браузере (можно добавить позже).
- Покрытие 100% кода.
- Серверные тесты.

## Что тестировать

| Функция | Сценарии |
|---|---|
| `calcProjectOverdueMonths` | дата в прошлом, сегодня, будущем; граница дня; невалидная дата |
| `calcGoalOverdueMonths` | то же |
| `isGoalOverdue` | статус «просрочено», «выполнено», «не выполнено», дата в прошлом |
| `getProjectHealth` | просрочка → red; перерасход → red; закрыт → closed; скоро закрытие без целей → yellow; всё ок → green |
| `buildReasons` | просрочка, перерасход, просроченные цели, пустой массив |
| `filters` | фильтр по направлению, проекту, комбинация, пустой результат |
| `errors` | 401, 429, 5xx, network, не-JSON |

## Сценарии

1. **Разработчик меняет правило.** Запускает `npm test`, видит, какие сценарии
   сломались, и исправляет код или тест.
2. **Коммит.** CI запускает `node --check` и `npm test`; красный статус блокирует merge.
3. **Ошибка API.** Пользователь вводит неверный ключ и видит:
   «Ключ не подошёл. Проверьте его в настройках DeepSeek», а не `HTTP 401`.
4. **Ошибка Excel.** Пользователь загружает пустой файл и видит:
   «Файл пустой. Загрузите Excel с проектами и целями».

## Технические заметки

- **Важно:** не переводить проект на ES-модули, если дашборд открывается через `file://` —
  браузер заблокирует импорты из-за CORS. Использовать классические скрипты + UMD:
  ```js
  (function (root, factory) {
    const api = factory();
    if (typeof module === 'object' && module.exports) module.exports = api;
    else root.Health = api;
  })(typeof globalThis !== 'undefined' ? globalThis : this, function () {
    // функции
    return { calcProjectOverdueMonths, calcGoalOverdueMonths, getProjectHealth, buildReasons };
  });
  ```
- `package.json`:
  ```json
  {
    "private": true,
    "scripts": {
      "test": "node --test tests/",
      "check": "node --check app.js && node --check health.js && node --check filters.js && node --check errors.js"
    }
  }
  ```
- CI: `.github/workflows/ci.yml`, Node 20, `npm test`, `npm run check`.
- Даты в тестах фиксировать, не использовать `new Date()` без подстановки `TODAY`.
  Для этого `getProjectHealth(project, today)` лучше сделать параметризуемой.
- Пример тест-кейсов — [payload.json](payload.json).
- Не добавлять зависимости, если хватает `node:test`.

## Риски и открытые вопросы

- Рефакторинг может незаметно изменить поведение — нужны тесты **до** переноса кода.
- `getProjectHealth` использует глобальную `TODAY`; параметризация изменит сигнатуру.
- CI в локальном проекте без git может быть не нужен — проверить, есть ли репозиторий.
- Нужны ли E2E-тесты в браузере (Playwright)?
- Нужен ли линтер (ESLint) или достаточно `node --check`?
- Кто отвечает за обновление тестов при изменении правил светофора?
